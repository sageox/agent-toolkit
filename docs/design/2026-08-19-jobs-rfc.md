# Jobs, archetypes, triggers, bounding, and verdict discipline — RFC

- **Status:** Proposed (design; no implementation in this RFC)
- **Date:** 2026-08-19
- **Author:** Madhur Shrimal
- **Closes:** [#35](https://github.com/sageox/buzz-agent-toolkit/issues/35)
- **Supersedes:** §10 of [the design spec](2026-08-12-multi-surface-agent-toolkit-design.md)
  (the `defineJob({collect, decide})` seam) — see §11.
- **Downstream:** the job declaration (§3–§8) is the schema every following item
  builds on; the migration order is §12.

This is a public repository. The evidence below cites file paths, line counts, and
generalized failure descriptions from the SageOx fleet — the same class of reference
[#35](https://github.com/sageox/buzz-agent-toolkit/issues/35) already makes. It carries no
secret paths, channel identifiers, keys, or role ARNs, and it should stay that way.

**Provenance.** §6.3 — the rule that a kill switch parks automation rather than the job
— comes from the design discussion that produced the job concept (Ryan, 2026-08-12),
surfaced through SageOx team context, and from the decision of 2026-08-11 that the fleet's
merge job already implements. Without it this RFC would have shipped a switch that locks
out the human trying to test a parked job.

---

## 1. The question

Seven of the twelve agents in the SageOx Buzz fleet do scheduled work, across twelve
jobs. Every one of them re-implemented cadence, trigger wiring, kill switches, and
cost bounding by copying from a sibling. This toolkit has no concept of scheduled work
at all, so the majority of that fleet cannot migrate onto it.

What should the toolkit own, and what must stay in the agent?

## 2. The answer: the toolkit owns the envelope, not the body

| The toolkit owns | The agent owns |
|---|---|
| The declaration — slug · archetype · trigger · description · kill switch · fail-direction | What the job actually does |
| Trigger evaluation (schedule / on-request / webhook) | The prompt, the diff, the PR body |
| Single-flight — an overlapping tick is dropped, loudly | Domain scope fences |
| Wall-clock budget below the deadline, and the deadline itself | Model choice per task |
| Kill-switch admission | — |
| The verdict contract | What the signals are |
| The run record and the status post, top-level + threaded detail | The words |

**The evidence for that line is the size of what is left over.** Bunyan's `runner/` is
37 source files of product logic; Whittle's is 11 (1,623 lines, and 2,718 with its
tests). None of it generalizes: `detectors.ts` shells out to `jscpd`, `readiness.ts`
grades a GitHub check rollup, `scope-fence.ts` knows which repository paths are
Sacred-tier. A toolkit that tried to own any of it would be describing one agent.

**The evidence for the envelope is the size of what repeats.** `shift-switch.ts` — the
kill-switch reader — exists in five runners at 329 lines each. Four of the five are
byte-identical (`md5` confirms it); the fifth has drifted by six lines. That is 1,639
lines of copied safety-critical code, and its own header says why it cannot be shared
today: *"SELF-CONTAINED ON PURPOSE — no `./log.ts` import. This file is copied verbatim
into every scheduled runner and they do not share a logging API."* The fleet has no
place to put it. This toolkit is that place.

The test, applied throughout: **would a second consumer with no SageOx fleet want it?**

### 2.1 The corollary — a bound the runtime can enforce blind is the toolkit's

The same test, sharpened for §7: a bound the runtime can enforce **without knowing what
the job does** belongs to the toolkit. A bound that requires counting the job's own
artifacts belongs to the agent. `wallClockMs` is a clock. `maxOpenPrs` requires knowing
what a pull request is.

## 3. The job declaration

A job is declared in `agent.yaml`, alongside the surfaces and brains it shares an
identity with. Not a second file, and not chart values: `docs/deployment-contract.md`
already requires that a deployment target *"preserve this contract instead of
translating `agent.yaml` into a second configuration model."* Jobs declared in Helm
values would be exactly that second model — which is how the fleet arrived at twelve
jobs described in six different charts.

```yaml
name: whittle
# … surfaces, brains, tools as today …

jobs:
  - slug: sweep
    archetype: sweep
    description: Whole-repo pass for logic that should live in a shared package.
    trigger:
      schedules: ["0 3 * * 0"]
      timezone: UTC
      onRequest: true
    killSwitch:
      failDirection: open          # required; no default (§6.1)
    suspend: true
    budget:
      wallClockMs: 3600000
      deadlineHeadroomMs: 300000
      harnessTimeoutMs: 600000
      maxIterations: 2
      maxAttempts: 3
      maxSpendUsd: 5
    model: claude-sonnet-5
    run:
      command: node
      args: ["runner/src/sweep.ts"]
    report:
      surface: buzz
      channel: hive
```

Schema, in the idiom of `packages/core/src/manifest.ts`:

```ts
export const JobSchema = z.object({
  /** Stable identity. Names the CronJob, the kill switch, and the run record —
   *  renaming one is a silent outage, not a tidy-up. */
  slug: z.string().regex(/^[a-z][a-z0-9-]*$/),
  archetype: z.enum(["watch", "shift", "sweep", "queue"]),
  /** One line, for an operator reading a roster they did not write. */
  description: z.string().min(1),
  trigger: TriggerSchema,
  killSwitch: KillSwitchSchema.optional(),
  /** The hard switch. A reviewed diff, not a memory write. */
  suspend: z.boolean().default(false),
  budget: BudgetSchema,
  model: z.string().optional(),
  run: z.object({ command: z.string().min(1), args: z.array(z.string()).default([]) }),
  report: z.object({ surface: z.string(), channel: z.string() }).optional(),
}).strict();
```

`description` is required and not decorative. A roster that cannot say what a job is
for cannot be reviewed by anyone who did not write it, and a parked job nobody can
describe is a job nobody restarts.

### 3.1 One prerequisite: the name must not already be taken

This RFC was written when the concept was called a *lane*, and `packages/core/src/queue.ts`
already declared `interface Lane` for a per-channel turn queue. Two meanings for one word
in one package is how a reader loses an afternoon, so the private one was renamed to
`ChannelState` before the declaration landed.

The collision outlived the fix. "Lane" was overloaded outside this package too — a CI
check lane, a swimlane, Fastlane's named task, and, in this team's own discussions, the
work territory an agent has claimed. The concept was renamed **job** on 2026-08-24, which
is the word every deployment target already uses for it and the one the fleet reached for
whenever it had to explain a lane. `interface Job` does not exist and must not: the queue's
per-channel state stays `ChannelState`.

### 3.2 `run.command` is an executable trust boundary

`loadManifest` parses YAML as *data* — `parseYaml` never evaluates it, and that is the
guarantee `manifest.ts` means by "data only, never executed". It is a guarantee about
**parsing**, not about what the parsed values later name. `jobs[].run.command` names a
process the host spawns, so anyone who can edit the bundle can choose what runs.

That is not a new boundary this RFC introduces: `mcpServers[].command` and
`brains[].command` already sit on exactly the same one, and a bundle has always been
code-equivalent. But an RFC that adds a spawn point should say so rather than leave a
reader to infer it from the parsing guarantee. **A change to `agent.yaml` gets the review
a code change gets** — and `run.command` is the field that makes that concrete.

Two constraints follow, and neither is speculative:

- The job host never builds `command` or `args` from a channel message, an issue body,
  a webhook payload, or any other untrusted input. Only the bundle names them.
- The list form (`command` + `args[]`) is the whole interface. No shell string, so
  nothing can be word-split or interpolated into a shell.

## 4. Archetypes: four, fixed, and documentation-only

#35 proposed five (`watch`, `shift`, `sweep`, `queue`, `call`) and asked whether the
taxonomy is right and whether the enum should be open.

**Fixed enum. Four values. `call` is dropped.**

| Archetype | What it names |
|---|---|
| `watch` | Event-reactive. A webhook fires it; narrow, fresh, cheap. |
| `shift` | The recurring bounded run. The workhorse. |
| `sweep` | Low-frequency, broad, expensive. Off-hours. |
| `queue` | Drains a work queue on request. No rhythm of its own. |

**The archetype carries no behavior.** It sets no defaults, gates nothing, and changes
no code path. It is an ops grouping label, deliberately redundant with the trigger. If
it carried defaults — `sweep` implying a larger budget, say — an author would choose
the label for its defaults rather than for the truth, and within two agents the
vocabulary would describe nothing. Behavior comes from `trigger`, `failDirection`, and
`budget`, each declared where a reviewer can see it.

**Membership test:** *would an operator ever act on every job of this kind at once,
across agents?*

- `sweep` — yes. These are the first thing you park under cost pressure.
- `watch` — yes. These fire outside your control during an incident; you park them as a set.
- `queue` — yes. Drain or don't drain the backlog during a freeze.
- `shift` — yes. The default population, and the one you audit.
- `call` — **no, structurally.** A human-summoned job is by definition acted on one at
  a time, by the human summoning it. It can never be a group action, so it can never
  earn a grouping label. And it names something the schema already says: `onRequest:
  true`. An archetype that duplicates a field is a second place for the same fact to be
  wrong.

**Fixed, not open**, for the same reason the labels exist: "suspend every `sweep`" is
only an operation if `sweep` means one thing everywhere. An open enum makes the
vocabulary per-agent, which is the state #35 was filed to escape. Adding a fifth is an
amendment to this RFC — cheap, but visible.

### 4.1 The retro-map, and where it contradicts #35

All twelve fleet jobs, from the charts as they stand:

| Agent · job | Trigger today | Archetype | Fail-direction |
|---|---|---|---|
| ashby · `arrivals` | cron `*/15` in working hours | `shift` | open |
| ashby · `scout` | cron `20 * * * *`, parked | `shift` | open |
| beekeeper · `rollcall` | cron daily | `shift` | open |
| bunyan · `shift` | cron `*/30` + on-request | `shift` | open |
| bunyan · `rip` | cron `*/10` | `shift` | **closed** |
| inkslinger · `shift` | cron `0 */6` + on-request + webhook | `shift` | open |
| inkslinger · `pr-review` | cron `0 */6` + on-request, parked | `shift` | open |
| monty · `cruise` | cron `40 7 * * 1-5` + on-request, parked | `shift` | open |
| whittle · `watch` | hourly backstop; wants a webhook | `watch` | open |
| whittle · `shift` | cron `0 */4` | `shift` | open |
| whittle · `sweep` | cron weekly | `sweep` | open |
| whittle · `queue` | fake daily cron; wants on-request only | `queue` | open |

Two things fall out that prose would have hidden.

**Eight of twelve are `shift`, and one archetype has no members at all.** That is the
honest shape of the fleet, and it is what killed `call`.

**#35's proposed mapping for Monty is wrong.** It reads *"Monty cruise→`call`"*, but
the chart declares a weekday cron with on-request as an escape hatch. It is a `shift`
that a human can also start — which is a trigger field, not an archetype. This is the
mapping error the taxonomy exists to prevent, caught on its first application.

Archetype assignments are proposals; each agent's owner confirms theirs when its job
declaration lands.

## 5. Triggers

```ts
export const TriggerSchema = z.object({
  /** Cron expressions. Two identical entries render two jobs on the same tick — refused. */
  schedules: z.array(z.string()).default([])
    .refine((s) => new Set(s).size === s.length, "duplicate cron expression"),
  /** IANA zone for every expression above. Cron alone cannot say which midnight. */
  timezone: z.string().default("UTC"),
  /** A human or a sibling may start this job now. Provenance is stamped, never argv,
   *  and only a human's request bypasses a parked switch (§6.3). */
  onRequest: z.boolean().default(false),
  /** An external event may start this job. */
  webhook: z.boolean().default(false),
}).strict()
  .refine((t) => t.schedules.length > 0 || t.onRequest || t.webhook,
    "a job with no trigger can never run");
```

### 5.1 A scheduleless job is legal here, and it is not in the fleet today

The fleet's chart schema *rejects* `onRequest` or `webhook` on a job with no schedule.
That restriction is a workaround, and the template's own header says so: the RBAC role
names are derived from rendered CronJob names, so a scheduleless job contributes no
name, the role comes back empty and vanishes without a render error, and *"the request
it advertised then 403s."* The header closes with *"bring it back when something needs
it."*

Something needs it. Whittle's `queue` job is conceptually on-request-only and had to
invent a daily 05:30 cron purely to exist as a schedulable object — a fake trigger
carried in production values with a comment explaining that it is fake. The toolkit
permits a job with zero schedules and `onRequest: true`, and that deletes the fake
cron on migration.

### 5.2 Quiet hours are declined

#35 asks for time-of-day/quiet-hours awareness as a declared property. **No field.**
Cron already expresses time of day, and the fleet already uses it that way — `0 3 * * 0`
*is* the quiet-hours declaration. A second overlapping window would give two ways to
say one thing and no rule for what happens when they disagree. What cron genuinely
cannot express is *which* midnight, so `timezone` is added and nothing else.

The gap that would justify revisiting: a `watch` job whose webhook fires at 3am and
whose cost profile makes that unacceptable. No such job exists. Revisit then.

## 6. Kill switches

Two switches, both toolkit-owned, unchanged in spirit from the fleet's:

- **Soft** — a value in the agent's memory (`mem/<slug>/enabled`), flippable in seconds
  without a deploy. Resolved through the brain the agent already declares — `local`,
  `private`, `shared`, or `team` — not a bespoke transport. A job that declares a kill
  switch on an agent with no brain is refused at load. Who may flip it, and in which
  direction, is §6.3.
- **Hard** — `suspend: true` in the declaration. Same effect, but it takes a reviewed
  diff to flip, and it is the one that survives an unreadable memory backend.

Both park **the clock** — see §6.3, which is the part most likely to be got wrong.

There is no third `enabled` flag. A job you never want is a job you do not declare;
a job you want on the roster but not running is `suspend: true`. The fleet's charts
carry `enabled` because a values overlay cannot delete a key, which is a Helm
constraint, not a design.

```ts
export const KillSwitchSchema = z.object({
  /** Defaults to `mem/<slug>/enabled`. Override only for migration compatibility. */
  key: z.string().optional(),
  failDirection: z.enum(["open", "closed"]),   // no default — see §6.1
}).strict();
```

**The key defaults to the slug.** Today one fleet job named `cruise` reads a switch
named `mem/shift/enabled`. Nothing is broken by it and nothing will be until the day
someone parks `cruise` by flipping `shift` and cannot find why a different job stopped.
Deriving the key from the slug removes the class; the explicit override exists so that
one job can migrate without a coordinated memory rewrite, and it is the exception, not
the pattern.

**A job with any unattended trigger (`schedules` or `webhook`) must declare a kill
switch.** Refused at load, not at 3am. This is the fleet's `cron-agent-kill-switch`
invariant, which its chart already enforces at render time — kept, and moved somewhere
a non-Kubernetes consumer also gets it.

### 6.1 Constraint 1 — fail-direction is declared per job, never inherited

`failDirection` has **no default**. Every job states it.

A job that acts on the world fails **closed**: the fleet's merge job, which lands
changes on `main` with no human in the loop, must never have *"we could not read the
switch"* be the reason an unattended merge happened. A job that only reports may fail
**open**: a relay blip must not silently halt reporting for days, and the hard switch is
behind it.

The fleet already gets this right — its merge job is fail-closed while its four
reporting jobs are fail-open — and it gets it right by having each runner pass a
different `unsetMeans` argument to a copied function. Copied defaults are exactly how a
sixth runner inherits the wrong one. Requiring the field costs one line per job and
makes the wrong direction unwritable by accident.

**Tests, not prose:**

1. `loadManifest` refuses a job declaring `killSwitch` without `failDirection`.
2. `loadManifest` refuses a job with `schedules` or `webhook` and no `killSwitch`.
3. Given one unreadable switch read, `admit()` returns denied for `failDirection:
   closed` and admitted for `open` — same input, opposite outcomes.
4. A manifest with two jobs of opposite fail-directions holds both under a single
   unreadable read (no shared mutable default between jobs).

### 6.2 Constraint 2 — "never configured" and "cannot read" are different words

A switch read returns a reading, never a boolean:

```ts
export type SwitchOrigin =
  | "set"          // a human wrote a value and we read it — the only case that is intent
  | "never-set"    // no value at the key. On a fail-closed job: NEVER ARMED
  | "unreadable";  // we could not look. Says nothing about intent

export type SwitchFailure =
  | "no-signing-key" | "no-owner" | "backend-missing"
  | "timeout" | "unreachable" | "auth-failed" | "backend-error";

export interface SwitchReading {
  state: "on" | "off";
  origin: SwitchOrigin;
  /** Only ever set when origin is "unreadable" — a never-set reading is a fact about
   *  the key, and hanging a "why it failed" off it would invent one. */
  failure?: SwitchFailure;
}
```

This is `shift-switch.ts`'s model, promoted. Its own comments carry the incident: a
fail-closed job sat unset for four days with twelve items waiting behind it, and
because "nobody ever set this" and "a human turned it off" both printed a bare `off`, a
config gap nobody had closed was indistinguishable from a state someone had chosen. It
surfaced because a person happened to ask. Separately, a fleet-wide memory-owner
misconfiguration meant *every* engram read and write failed at once — so no fail-closed
job could ever be armed, and the human trying to arm it by message got the same silent
refusal — and that hid for weeks behind a status that read normal.

`SwitchFailure` is a closed vocabulary and never the exception text, for two reasons the
fleet learned separately: the raw message carries the whole command line and backend
stderr onto whatever surface renders it, and each class sends a human somewhere
different — `backend-missing` is a broken image, `auth-failed` is an unseeded key,
`unreachable` is an outage to wait out.

**Classification runs the safe way round.** Only a documented not-found answer may be
read as `never-set`. Anything unrecognized falls through to a failure class. If a
backend rewords its not-found response, this degrades to "we could not read it" — still
distinguishable from "a human parked me", which was the whole point — rather than to a
lie.

**Tests, not prose:**

1. `describeSwitch` renders `never-set`, `unreadable`, and `{state:"off", origin:"set"}`
   as three pairwise-distinct strings.
2. A not-found response classifies as `never-set`; a network failure, an auth failure, a
   missing backend binary, and a timeout each classify as `unreadable` with their own
   `failure`.
3. A missing-owner refusal classifies as `no-owner`, never `never-set` — the read never
   reached a key, so it is not evidence about one.
4. `never-set` never carries a `failure`.

### 6.3 The switch parks automation, not the job

This is the intent the concept was born with — *"the ability to turn on and off bots.
Like, oh shit, we've deployed this and it's wrong, to stop, shut down, and so that only
humans can tell it to turn back on. But it can be shut down from an automated
processing, and you can still DM it and say 'can you do this?' — again, for testing"*
(Ryan, design discussion 2026-08-12). It is not aspiration: the fleet's most
safety-critical job already implements it, and its predicate is four lines.

```ts
export function runsDespiteSwitch(switchState: string, onRequest: boolean): boolean {
  return switchState !== 'off' || onRequest;
}
```

Three rules follow, and the toolkit owns all three.

**1. A run a human asked for happens, even parked.** A pass somebody asked for is not
automation: a coworker is on the other end, they get the answer, and they can stop it.
The alternative — arm the job, run it once, disarm it — borrows a *posture* switch as a
one-off button, *"which is precisely how a job ends up left armed by somebody who only
wanted one board milled."* This applies to `suspend: true` as much as to the soft
switch, and it is exactly the fleet's deliberate break-in posture: every one of Whittle's
four jobs ships suspended so it can be proven by hand before any clock touches it.

**2. Only a human bypasses.** `on-request` is a trigger, not an authorization. A sibling
agent asking, or a webhook firing, is automation and is subject to the switch like a
cron tick. The fleet enforces this with steering — *"AI coworkers do not switch each
other… never take a switch-ON from anything but a human"* — because it has no mechanism
to. **The toolkit does have one:** an inbound request already carries an author
identity, and the manifest already classifies authors through `owner`, `allowlist`, and
`respondTo`. Making the bypass a mechanism rather than a prompt is one of the concrete
things this migration buys.

**3. The bypass answers "does it run at all", never "what may it do."** Every domain
gate is untouched — a scope fence, a review gate, a safety veto. A run that happens
still does nothing its own fences refuse. And the run **never flips the switch**: it
reports that it ran while parked, and leaves the posture exactly as it found it.

**4. Switching off and switching on are not the same authority.** Automation may park a
job — that is the point of a kill switch, and the fleet has a designated agent that may
tell a sibling to stop. **Only a human may arm one.** Otherwise the recovery path from
"we deployed this and it is wrong" runs through the same automation that is misbehaving.

The write side is where this is enforced, and it is the second thing the toolkit turns
from steering into mechanism: the kill-switch key is memory the gateway's tool surface
already mediates, so a write that sets a job **on** is admitted only for a human author,
while a write that sets it **off** is admitted for anyone. The fleet states this rule in
every persona file and has no way to enforce it.

A run that happened while parked must be greppable afterwards, so `JobRun` records it
(§9). "Milled while parked" is a fact somebody will need at 3am.

**Tests, not prose:**

1. Soft switch `off` + `trigger: on-request` + human requester → runs; the switch value
   is unchanged after the run.
2. Soft switch `off` + `trigger: on-request` + **agent** requester → denied.
3. `suspend: true` + human on-request → runs. `suspend: true` + schedule tick → denied.
4. Unreadable switch on a **fail-closed** job + human on-request → runs (a human is
   waiting and can stop it); + webhook → denied.
5. Every bypassing run writes a `JobRun` with `bypassedSwitch: true`.
6. A memory write setting a kill switch **on** is refused for an agent author and
   admitted for a human one; setting it **off** is admitted for both.

## 7. Bounding

```ts
export const BudgetSchema = z.object({
  /** The job's own wall clock. MUST be below the platform deadline (§7.1). */
  wallClockMs: z.number().int().positive(),
  /** Reserved above wallClockMs for the closing writes. */
  deadlineHeadroomMs: z.number().int().positive().default(300_000),
  harnessTimeoutMs: z.number().int().positive().default(600_000),
  maxIterations: z.number().int().positive().default(2),
  maxAttempts: z.number().int().positive().default(3),
  maxSpendUsd: z.number().positive().optional(),
}).strict();
```

Ported from the fleet's bounding kit, which is the hardest-won safety code it has. The
budget bows out **before** the deadline rather than being cut off at it: a SIGKILLed
process runs no cleanup, so a claimed item stays claimed and a half-written change is
left dangling. Every stage that can block for minutes checks the budget first and caps
its own timeout by what remains.

Spend is the same shape on a different axis: the job records what it has spent and
declines a call it cannot afford, rather than discovering the cap by crossing it.

Three details worth carrying verbatim, each of which was a bug first:

- **A non-finite bound throws at construction.** `NaN` comparisons are always false, so
  a poisoned budget waves every call through instead of bowing out — it fails in the
  unsafe direction, silently.
- **A negative recorded spend clamps to zero.** It must never buy back budget already
  used.
- **An unaffordable estimate that cannot be reasoned about is treated as unaffordable.**
  Fail closed on arithmetic you do not trust.

### 7.1 The deadline is derived, never set twice

`wallClockMs + deadlineHeadroomMs` **is** the platform deadline
(`activeDeadlineSeconds`, a launchd timeout, a workflow `timeout-minutes`). The
declaration carries the two parts; the deploy target computes the sum. An operator who
can set both the budget and the deadline independently will eventually set the deadline
below the budget, and the failure is the SIGKILL-mid-write one above.

### 7.2 What stays agent-side

`maxOpenPrs` (the WIP cap / fix-job freeze), `maxIssuesPerShift`, `maxFiles`,
`maxTotalLines`, and the scope fence's denied path prefixes. Each requires knowing what
the job produces (§2.1). They stay in the runner's own config, read by the runner and not
by this host — from a file beside the code that reads it, or from an environment variable
the bundle declared in `run.env`, which is where a job body's environment comes from
([the job body contract](../job-contract.md#what-the-host-passes-in)).

### 7.3 The spend-capped provider workspace is doctrine, not machinery

The fleet's runaway-cost backstop is a per-agent Anthropic Console workspace with a hard
monthly cap. The toolkit cannot create one, cannot read one, and cannot verify one — so
it must not imply it has. It belongs in
[the fleet doctrine doc](../fleets-and-the-mayor.md#the-spend-cap-the-toolkit-cannot-enforce)
as a required operator step, and nowhere in this schema. Claiming a control the runtime
does not hold is the same defect as a composed verdict, one level up.

## 8. Verdict discipline

**Run the tool. Never compose the verdict.** The toolkit exports the verdict type and
its only constructor, and there is deliberately no function anywhere in it that turns a
claim, a sentence, or "it looks right" into a `PASS`.

```ts
export type VerdictStatus = "PASS" | "FAIL" | "UNKNOWN";

export interface GateResult {
  gate: string;
  /** Did the gate process START? Nothing about how it ended — see `exitCode`. */
  executed: boolean;
  /** What it said on the way out. `null` when it never said anything. */
  exitCode: number | null;
  detail?: string;   // a path, a count — never used to decide
}

export function verdictFromGate(r: GateResult): Verdict;
export function combineVerdicts(vs: readonly Verdict[]): Verdict;
export function describeVerdict(v: Verdict): string;
export function isProven(v: Verdict): boolean;
```

**The two fields are orthogonal, and that is deliberate.** `executed` answers *did it
start*; `exitCode` answers *what did it say*. A gate killed or timed out mid-run is
`{executed: true, exitCode: null}` — it started, and it never got to speak. The
inherited wording for this field read *"ran to completion"*, which collides with that
case: a producer reading the comment would serialize a killed gate as `executed: false`
while a producer reading the rules would serialize it as `true`. Both still yield
`UNKNOWN`, so no verdict was ever wrong, but the artifact in §8.2 is JSON another
process reads, and two encodings of one state is a defect there. **Implementers should
take this wording over Whittle's**, which has the older comment.

| Gate state | `executed` | `exitCode` | Verdict |
|---|---|---|---|
| Never started | `false` | `null` | `UNKNOWN` |
| Started, killed or timed out | `true` | `null` | `UNKNOWN` |
| Started, exited non-zero | `true` | `n` | `FAIL` |
| Started, exited 0 | `true` | `0` | `PASS` |

`PASS` is returned on exactly one input shape — the last row. `combineVerdicts` is
conservative: any `FAIL` dominates, else any `UNKNOWN` dominates, and an empty list is
`UNKNOWN`, because "no gates ran" is never success.

`describeVerdict` is the render-time half, and it is load-bearing: the fleet's
anti-fabrication incidents were rendering bugs at least as often as logic ones — a
source that could not be read rendered as a clean report, and a liveness check with no
ability to read state answered confidently anyway. `UNKNOWN` and `FAIL` renderings must
contain no word a skimming reader could mistake for success, and that is a test.

### 8.1 This supersedes `{ signals, ok }`

#35 sketches a verdict wrapper as `{ signals, ok }` plus a deterministic gate. Adopt the
shape above instead: **`ok: boolean` cannot express `UNKNOWN`**, and `UNKNOWN` is the
entire point. A two-valued verdict forces every unproven result into one of its
neighbours — rounding to `ok` hides outages, rounding to not-`ok` cries wolf until
nobody reads the report. Say you do not know.

### 8.2 How a job reports one

The job body writes its verdict to `$JOB_VERDICT_PATH` as JSON. The host reads it
after the process exits.

**A missing or unparseable artifact is `UNKNOWN`.** Not an error, not a pass — the
fail-safe falls out of the file's absence rather than out of someone remembering to
handle it. A job that ran, exited 0, and reported nothing has proven nothing.

The artifact is also what makes the chat face honest. The structural fix for *"an agent
asked a question it cannot truthfully answer will answer it anyway"* is not a prompt: it
is giving the conversational surface a **read tool for the artifact** instead of a
capability it half-has. The chat face quotes a timestamped verdict it can actually read.
It cannot invent one.

## 9. The run record and the status post

Every run writes a `JobRun` — always, including a run the kill switch denied and a tick
dropped for overlap:

```ts
export interface JobRun {
  jobSlug: string;
  runId: string;
  /** Stamped by the host from how the run was started. Never an argv flag. */
  trigger: "schedule" | "on-request" | "webhook";
  /** Who asked. Resolved from the inbound author, never self-reported (§6.3). */
  requestedBy: { kind: "human" | "agent" | "system"; id: string } | null;
  startedAt: number;
  endedAt: number | null;
  outcome: "completed" | "denied-switch" | "denied-suspend"
         | "skipped-overlap" | "budget-bowout" | "crashed";
  switch: SwitchReading | null;
  /** True when a human ran this job while it was parked (§6.3). */
  bypassedSwitch: boolean;
  verdict: Verdict;
}
```

**Silence is allowed for findings. It is never allowed for the run record.** A job that
found nothing posts nothing to a channel — the fleet's rule, and it is right. But the
record is always written, because a job that reported nothing and a job that never ran
must not render the same. That is §6.2's constraint one level up, and it is the same
mistake both times.

The status post's *shape* is the toolkit's: a one-line verdict at top level, detail in a
thread beneath it. Headlines scroll; detail threads. The *words* are the agent's.

**Trigger provenance is stamped by the host**, from which entry point started the run —
not passed in. A job body that could name its own trigger could claim a human asked for
something a clock started.

## 10. Single-flight

**In one job-host process:** a mutex per slug. An overlapping tick does not queue and
does not silently vanish — it is dropped, and it writes a `JobRun` with outcome
`skipped-overlap`. "Loudly" means it leaves a record, not that it pages anyone.

**Across processes:** the platform provides it. A Kubernetes CronJob declares
`concurrencyPolicy: Forbid`, and the toolkit's chart renders that unconditionally. This
is honest about a real limit — `Forbid` cannot see across two objects, so two schedules
on one job, or a webhook pod and a cron pod, can overlap. That is not hypothetical: one
fleet job already declares schedules *and* on-request *and* webhook.

A cross-process lease is **out of scope for D0** and named in §14 as the first thing to
build if a job arms two independent trigger sources at once. Until then the schema
refuses duplicate cron expressions on one job, which is the case the fleet's chart
already had to catch by hand.

## 11. Relationship to §10 of the design spec

The design spec's §10 proposed a Job SDK with a `defineJob({ collect, decide })` seam — an
earlier and unrelated use of the word, and a *callback* API rather than a declaration.
**That seam is withdrawn**, not the concept this RFC declares. It was written before there was evidence about job bodies,
and the evidence contradicts it: Bunyan's ~30 files and Whittle's 15 do not decompose
into `collect` and `decide`. Whittle's shift alone is a WIP-freeze check, a delta
against a committed baseline, a ranked selection, a coding harness call, a scope fence,
a verdict gate, and a draft-PR publication with a readiness declaration. Forcing that
into two callbacks would produce a `decide` that is the whole program and a toolkit that
describes one agent.

The `run: { command, args }` seam replaces it. The toolkit spawns a process, hands it
the envelope, and reads its verdict artifact. A job body may be TypeScript, a shell
script, or a compiled binary — the contract is a process, an exit code, and a file.

**Two parts of §10 survive intact.** The "scheduled turn" tier — a clock tick entering
as a synthetic inbound event through the ordinary brain → guard → egress path — is
unchanged and remains the right answer for light work; it needs no job declaration and
no separate process. And "on-request vs scheduled is unforgeable provenance stamped by
the trigger, not an argv knob" is §9 above, verbatim.

## 12. How the fleet migrates

The declaration is the source of truth. Helm cannot read an operator-supplied bundle at
render time, so the toolkit CLI **generates** job values from the manifest and `doctor`
fails when the two diverge. One source, mechanically enforced, for as long as the
generated intermediate exists.

Per agent, the migration **deletes** rather than ports:

| Deleted | Lines |
|---|---|
| `runner/src/shift-switch.ts` × 5 | 1,639 |
| Per-chart job boilerplate (Whittle's four jobs are ~90% identical) | ~180 in one chart |
| The fake backstop cron on Whittle's `queue` job | 1 trigger, and its comment |

`verdict.ts` is not a deduplication win — it exists in one runner. It is a prevention
win: every future job gets it without deciding to.

**Order, by blast radius:**

1. **Whittle's four jobs.** Every one ships `suspend: true` by deliberate posture, so
   nothing is in production to break, and it is the only agent that exercises every
   archetype. It is the migration's own test case.
2. **The parked jobs elsewhere** — Ashby's `scout`, Inkslinger's `pr-review`, Monty's
   `cruise`. Monty's is where the switch-key override earns its keep.
3. **The live fail-open jobs** — Ashby's `arrivals`, Beekeeper's `rollcall`,
   Inkslinger's `shift`, Bunyan's `shift`.
4. **The merge job, last and alone.** It is the fleet's only fail-closed job and the
   only one that lands changes on `main` unattended. It moves after the model has run
   in production for the other eleven.

## 13. What the toolkit does not own

Stated so it cannot drift: the job body, the prompt, the diff, the PR body, domain
scope fences, per-task model choice, what counts as a signal, the words of any status
post, the fleet roster, and the roll call that reads it. A roster is a fleet concept,
not a runtime one; it stays with the fleet, and the doctrine for it is
[a separate document](../fleets-and-the-mayor.md).

## 14. Open decisions

1. **Cross-process single-flight.** A lease, and where it lives. Needed the day a job
   arms two independent trigger sources at once (§10). One fleet job already declares
   three.
2. **A job with an identity that is not the agent's.** The fleet's merge job runs in
   another agent's chart with its own signing key and its own secrets. Does the
   declaration carry an identity override, or is such a job simply its own agent with
   no surfaces? The second is cleaner and is the recommendation, but it is a real
   migration cost and belongs to whoever moves that job.
3. **How `report.channel` resolves.** A symbolic name here, an identifier in a
   deployment. Small, but it is where a channel identifier would otherwise leak into a
   public bundle.
4. **Quiet hours** (§5.2) — declined, with a named condition for revisiting.
5. **How a run started outside a chat surface proves it is human** (§6.3). A request
   arriving through Buzz or Slack carries an author the manifest can already classify. An
   operator running the CLI against a cluster is just as unambiguously human, and a CI
   dispatch is not — but neither carries an author the host can read. Until this is
   settled, those paths are `requestedBy.kind: "system"` and do **not** bypass a parked
   switch, which is the safe direction and slightly annoying for the operator.

## 15. Summary of decisions

| # | Decision |
|---|---|
| 1 | The toolkit owns the envelope; the job body stays in the agent (§2). |
| 2 | Jobs are declared in `agent.yaml`, not in chart values (§3). |
| 3 | Four archetypes — `watch`, `shift`, `sweep`, `queue`. Fixed enum, documentation-only, no behavior (§4). |
| 4 | `call` is dropped: it can never be a group action, and it duplicates `onRequest` (§4). |
| 5 | A scheduleless on-request job is legal (§5.1). |
| 6 | No quiet-hours field; `timezone` instead (§5.2). |
| 7 | The kill-switch key defaults to the slug; the override is a migration exception (§6). |
| 8 | `failDirection` is required per job, with no default (§6.1). |
| 9 | A switch read returns `{state, origin, failure?}`, never a boolean (§6.2). |
| 9a | Both switches park the clock. A human's on-request run happens anyway; an agent's or a webhook's does not (§6.3). |
| 9b | The bypass decides only whether a run happens, never what it may do, and never flips the switch (§6.3). |
| 9c | Anyone may park a job; only a human may arm one, enforced on the memory write (§6.3). |
| 10 | The platform deadline is derived from the budget, never set independently (§7.1). |
| 11 | Artifact-counting bounds stay agent-side (§7.2). |
| 12 | The verdict is three-valued; `{signals, ok}` is superseded (§8, §8.1). |
| 13 | A missing verdict artifact is `UNKNOWN` (§8.2). |
| 14 | The run record is always written; only the channel post is conditional (§9). |
| 15 | §10 of the design spec's `defineJob` seam is withdrawn; `run: {command, args}` replaces it (§11). |
