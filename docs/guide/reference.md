## Files this creates

Everything one agent owns lives in `~/.config/agent-toolkit/agents/<name>/`:

| File | What |
|---|---|
| `agent.yaml` | what the agent is and who it answers |
| `AGENTS.md` | its persona — the voice is yours to write |
| `profile.json` | its complete public profile — display name, about line, NIP-05, avatar |
| `avatar.md` | its style-independent character brief |
| `avatar.svg` | its offline starter badge and fallback upload source |
| `avatar.png` | its generated artwork when image generation was selected |
| `settings.json` | what its tools may do |
| `repos.conf` | optional HTTPS repositories to clone; prefix private GitHub repositories with `private ` |
| `.env` | credentials, mode 600 |
| `state.json` | resume cursors |
| `workspace/` | durable repository checkouts and `ox` code indexes |
| `brain/` | the local memory vault, once you add one |

A default shared vault lives under `~/.config/agent-toolkit/agents/shared/`, beside the
participants rather than inside either one. An explicit `--path` can put it on a shared
volume instead.

The bundle stays independent of a source checkout. Deployment configuration and secret
material live outside it and are supplied by the chosen deployment integration.

## Credentials, and where they live

| Credential | Needed for | Where |
|---|---|---|
| `ANTHROPIC_API_KEY` | the real brain | prompted by `brain claude` |
| `BUZZ_NSEC` | signing Buzz events | generated by `identity create` or saved by `identity attach` |
| `SLACK_BOT_TOKEN` | Slack Web API (`xoxb-`) | prompted by `surface slack` |
| `SLACK_APP_TOKEN` | Slack Socket Mode (`xapp-`) | prompted by `surface slack` |
| `SAGEOX_TOKEN` | the team brain (the default; `token:` can name another) | local `.env`; deployment secret binding when hosted |
| `GITHUB_TOKEN` | repositories marked `private` in `repos.conf` | local `.env`; deployment secret binding when hosted |
| anything an MCP server needs | that server | prompted by `mcp add` |

You are never asked to edit `.env` yourself.

`.env` is the local-development tier. Deployment adapters mask it and mount externally
managed files at `/mnt/secrets-store`. **The manifest never changes** — it names a reference, and
the deployment decides where that reference resolves.

## Naming tools in the policy

MCP tools reach the brain **namespaced**: `mcp__<server>__<tool>`, with anything outside
`[a-zA-Z0-9_-]` in the server name replaced by `_`. A policy that allows a bare
`team_search` matches nothing.

| brain | server | tools |
| --- | --- | --- |
| `local` | `brain` | `mcp__brain__brain_list`, `mcp__brain__brain_read`, `mcp__brain__brain_write`, `mcp__brain__brain_consolidate` |
| `shared` | `brain-shared-<n>` | the same four, under that server |
| `private` | `private-brain` | `mcp__private-brain__brain_list`, `mcp__private-brain__brain_read`, `mcp__private-brain__brain_write`, `mcp__private-brain__brain_delete` |
| `team` | `team-brain` | `mcp__team-brain__team_search` |

Any server you add is namespaced the same way, under the name you gave it — a server named
`github` publishing `pr_list` is `mcp__github__pr_list`. `mcp add` reads the live tool list
and writes those strings for you, which is the point: a bare name matches nothing.

So is the job surface, under `jobs`: `mcp__jobs__job_run`, which lets a conversation
start one of the agent's own jobs. Only jobs that declare `trigger.onRequest` are offered,
the slug is the whole of what the tool takes for a job that declares no `parameters` — the
argv is always `run.command` and `run.args` from `agent.yaml`, and nothing in the call
reaches it — and a run asked for this way is recorded as `agent`, so it does **not** bypass
a job that is parked or `suspend: true`. A job that declares `parameters` also takes those,
under `params`, typed and bounded by its own declaration and refused at the call if they do
not match; they reach the body as `JOB_PARAM_<NAME>` in its environment. They name a
**target** — which issue, which document, which environment — and never a behaviour: a job
whose work a caller can switch is two jobs with two slugs. See
[the job body contract](../job-contract.md). A job short enough to finish inside a turn is
waited for and the tool answers with its verdict; a job whose `wallClockMs +
deadlineHeadroomMs` is longer than `limits.turnTimeoutMs` is **started** instead, and the
tool answers with the run id and nothing that reads as a verdict — the verdict arrives later,
as the job's ordinary status post. Give such a job a `report` destination, or it has
nowhere to answer and `doctor` will say so. Add it with `sageox-agent mcp add jobs`, which
refuses when no job has armed that door — the tool is served for those jobs and no others,
so allowing it first writes a permission for something that will never exist. The reverse,
a job that declares `trigger.onRequest` while the policy denies the tool, is a `doctor`
failure: nothing could ask for it, and the agent reads as one that cannot run its own jobs
rather than one not allowed to.

`memory add` and `mcp add` write these for you. Reach for this table only when editing a
policy by hand — and `doctor` will tell you if you get it wrong.

## What the log says about tool calls

Every MCP tool call writes one line, whether it ran or not:

```
tool_call tool="mcp__github__pr_create" outcome=ok ms=412 args={"repo":"acme/service","head":"<string 6>","base":"<string 4>","title":"<string 18>","body":"<string 1300>"}
tool_call tool="mcp__github__issue_create" outcome=refused ms=0 reason="mcp__github__issue_create refused: this server is bound to repo ∈ {acme/service} …" args={"repo":"acme/other","title":"<string 12>"}
```

`tool` and `reason` are quoted because both can carry text the caller chose — a tool name
arrives as whatever the brain asked for. A newline in an unquoted field would end the
record and write a second one, and a forged `outcome=ok` is precisely what would send you
past the call you were looking for.

`outcome` is one of three, and the difference is the point:

| `outcome` | What happened |
|---|---|
| `ok` | The tool ran and answered. |
| `refused` | A gate stopped it before it ran — the tool policy, or a write tool that is not armed. `reason` names the rule. |
| `failed` | It ran and did not work. `reason` is what it said. |

**A refusal is the line to watch.** One means a bundle is misconfigured — the tool is in
the manifest and not in the policy, and `doctor` will name it. A stream of them, on an
agent whose surfaces read channel content anybody can post to, is something asking for a
capability it does not hold, and that is the signal the tool policy exists to produce.

The line is bounded everywhere the caller can reach it: at most 32 arguments are named, a
name is cut at 120 characters, a value at 200, and a declared list at 8 items. Whenever
something was dropped the record says how many there really were — `"…":"<200 arguments>"`,
`"<4900 items>"` — so a shortened record never reads as the whole call. A cut *name* keeps a
128-bit digest of the whole one, so two long names that begin alike stay two names — and
stay apart even when a caller builds them to collide: a record that cannot say which tool ran has failed at the only thing it does. Real
calls are never shortened; every one of these bounds sits well above what a working tool
sends.

**Arguments are recorded by declaration, and the default is to record none.** Each tool
names the arguments whose *values* may be written down — a repository, a branch, a job
slug, a channel, a memory key. Everything else is written as a type and a size:
`"body":"<string 1300>"` says a description was passed and how long it was, and holds none
of it. Free text is never recorded — not a pull request body, not a message the agent
posted, not a `team_search` query, which is whatever somebody asked the agent in a channel.
Nor is anything from a server the broker runs: its tools come from your manifest and a
third-party process, so nothing in the toolkit knows which of its arguments are safe, and
it records all of them as shapes.

The line is for you and the brain never reads it — the same split the guard makes between
the reason it hands back and the `egress_blocked` line it writes. There is no sink, no
retention and no shipping: it goes to the gateway's stream beside `turn_start` and
`ox_failed`, and wherever you already send that is where it lands.

## The team brain's credential

`ox` has no interactive login in a container, so it takes a **personal access token** in
`SAGEOX_TOKEN` — its documented path for "CI/CD, headless agents, ephemeral containers."
Create one at **https://sageox.ai/settings/tokens**; it is prefixed `oxp_` and shown once.

One thing to know: `doctor` checks the token with SageOx and reports its current rolling
expiry. If SageOx rejects it, rotate the value through the deployment's secret manager and restart
only the affected agent workload.

Do not reuse the access token from your own `ox login`: it expires within hours and has no
refresh credential once out of ox's hands.

`token` names the secretRef the token is read from — never the token itself. It defaults to
`SAGEOX_TOKEN`, so set it only when several agents on one host each carry their own:

```yaml
brains:
  - preset: team
    team: team_xxxxxxxx     # the team ID from `ox teams`, not its slug — a slug 403s
    token: OX_TOKEN_ASHBY   # a secretRef; the gateway resolves it, the brain never sees it
```

**A token is bound to one endpoint.** ox uses it for `SAGEOX_ENDPOINT` when that is set, and
otherwise only for `https://sageox.ai`. Against any other endpoint it is not rejected — it is
not used, and ox falls back to `auth.json`: no credential at all, or a different identity than
the one you configured. Team memory is on production, which is already the default, so leave
`SAGEOX_ENDPOINT` unset unless you mean it.

The alternative, for a credential that renews itself, is mounting a logged-in `auth.json`:

```yaml
brains:
  - preset: team
    team: team_xxxxxxxx
    configHome: /mnt/secrets-store/ox   # holds sageox/auth.json
```

Set `BRAIN_MCP_HOST` when the brain runs in a separate container and needs a routable
address; it defaults to `127.0.0.1`.

## What resumes after a restart

`state.json` in the agent's directory holds the newest message seen per surface, so a
restart re-subscribes from there rather than opening a deaf window over whatever arrived
while it was down. Written every 30s and on clean shutdown.

Delete it — or start on a volume that never had one — and the agent begins at the last
minute, not the beginning of the channel. It does not read back what the channel already
holds: a stored message it never saw is not one it was asked to answer, and an agent whose
replies open pull requests would be acting on a week of settled requests. The minute is
there because a message carries its author's clock, not the agent's, so one published a
moment ago can be stamped a little behind.

Repository checkouts and code indexes also survive under `workspace/`. Each start verifies
the checkout's origin, runs a fast-forward-only pull, and refreshes the index in the
background.
